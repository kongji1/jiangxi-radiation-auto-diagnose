# 终审成功后报告刷新修复（0.8.56）

## 已确认原因

只读服务器操作记录证明终审已成功，重新打开的原生界面也显示已审核。旧页面继续显示诊断中和编辑保存失败，不能据此重提终审。

原生终审向 `/api/ct/rays/rep/report` 提交成功后，调用 `getRadiationDetail`，再次 POST `/api/ct/rays/rep/enter` 回读报告。0.8.55 提前取得响应后，交接记录永久停在 `consumed`；桥把所有相同进入请求当作重复取得，在本地返回 HTTP 0。原生回读因此失败，界面保留旧状态，后续自动保存又因服务器已审核而失败。终审和自动保存接口本身未被桥拦截。

## 修复边界

`src/13-protocol-bridges.js` 增加 `loaded` 确认：初始响应成功交付，而且旁听到当前报告、路由、响应 UID、当前医生和同一会话的成功 POST 后，才允许原生后续刷新。XHR 必须完成成功事件交付；fetch 必须构建合法 Response，确认之前的中止不能释放防重。

已确认交接记录继续保留，阻止再次提前取得。初始并发、未确认、中止、过期、丢弃、归属或身份不符均保留本地防重。自动进入一次记录、其它用户锁定门禁、配置和开发者日志不改动。`report` 与 `autoSaveRep` 原生透明转发。

## 验证与加载

针对真实源码的隔离夹具覆盖：终审提交成功后原生刷新、自动保存透传、初始并发、中止、错 UID/路由/医生/会话。发布执行登记表全部测试。不重放真实报告进入、锁定或终审请求。

Tampermonkey 保存与当前执行上下文分别证明；活动报告页不能为维护强制重载。旧 0.8.55 桥为冻结对象，仅保存新脚本不替换旧文档闭包；兼容热修复必须保持每份报告的防重记录，不允许全局清空交接表。实际部署记录写入 `PROJECT_STATE.json.reportRefreshRepair`，不改写历史验证。

本次 Edge 9333 已隐藏保存 0.8.56，并读回安装 SHA 与源码相同。当前会话的一个既有报告使用严格历史加载证据释放后续原生刷新；另一报告的旧 ticket 与当前共享会话已不同，不修改该 ticket。两份报告均保持编辑内容和配置指纹一致，没有报告页重载；返回列表后一次加载新版。完整旧运行版本和兼容补丁标记分别记录。

兼容入口：`python -B tools/repair-report-refresh-cdp.py --target <明确报告targetId>` 默认只安排列表加载。只有已独立确认初始成功载入时才能加 `--confirmed-transport`，它在页面内核对成功记录、UID、医生、会话、规范 payload 和已消费 ticket；未确认或会话变化不释放。工具验证新源码确实已安装，不调用业务接口，不记录任何病例、会话值或编辑内容。`tools/report-refresh-compat.mjs` 有 18 项专项夹具，已登记全量验证；兼容标记不代表完整脚本运行版本。

## 快速排查

`maintain-project.py diagnose --name "客户姓名" --with-audit --date YYYY-MM-DD` 已支持显式服务器只读审计。默认诊断仍只读取现有日志。优先比对服务器最终状态、成功提交后的回读和本地 HTTP 0，不把界面保存警告直接等同于终审失败。
